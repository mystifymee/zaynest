# Zaynest

Telegram-бот для демонстрации заказа клининга. Он принимает заявки на поддерживающую и генеральную уборку, рассчитывает стоимость по площади и сохраняет заказы в PostgreSQL 17. Администратор получает уведомление и управляет заказами через `/orders` в личном чате.

## Локальный запуск

Понадобятся Node.js 22.12+ в ветке 22 или Node.js 24, npm и Docker с Compose. Выполните из корня репозитория.

```sh
docker compose up -d db
docker compose exec -T db pg_isready -U zaynest -d zaynest
cd server
test -f .env || cp .env.example .env
chmod 600 .env
npm ci
npm run db:generate
npm run db:deploy
npm run db:status
npm run dev
```

Перед запуском `npm run dev` заполните `BOT_TOKEN` из @BotFather и `ADMIN_TELEGRAM_ID` числовым Telegram user ID администратора в `server/.env`. Администратор должен открыть личный чат с ботом и отправить `/start`, чтобы бот мог присылать уведомления. Используйте один процесс long polling на токен.

`docker compose up -d db` использует существующий локальный том и порт `127.0.0.1:5433`. Миграция добавляет таблицу черновиков, ключи подтверждения и переводит статус в enum. Исторические заказы с пустыми полями Telegram ID и ключа доступны администратору. Если в базе есть статусы вне четырёх поддерживаемых значений, миграция откатится. Перед обновлением базы с данными сделайте резервную копию и проверьте нестандартные статусы. После обновления схемы Prisma применяйте сохранённые в репозитории миграции через `npm run db:deploy`.

## Проверки

Из `server/` после установки зависимостей и генерации клиента.

```sh
npm run typecheck
npm run build
TZ=UTC npm test
TZ=America/Los_Angeles npm test
```

Интеграционный тест использует отдельную PostgreSQL, сохраняет синтетические записи для проверки и подменяет сетевые вызовы Telegram. Из корня репозитория можно поднять тестовую базу следующими командами.

```sh
docker run -d --rm --name zaynest-pg-test \
  -e POSTGRES_USER=zaynest -e POSTGRES_PASSWORD=isolated_test_only \
  -e POSTGRES_DB=zaynest_test -p 127.0.0.1:55433:5432 postgres:17-alpine
docker exec zaynest-pg-test pg_isready -h 127.0.0.1 -U zaynest -d zaynest_test
cd server
export TEST_DATABASE_URL=postgresql://zaynest:isolated_test_only@127.0.0.1:55433/zaynest_test
DATABASE_URL="$TEST_DATABASE_URL" npm run db:deploy
npm run test:integration
unset TEST_DATABASE_URL
docker stop zaynest-pg-test
```

## Первый запуск на VPS

Установите Docker Engine и плагин Compose. На сервере с systemd включите запуск Docker при загрузке командой `sudo systemctl enable --now docker`. Перенесите проверенную версию проекта на сервер и выполняйте команды из его корня.

```sh
test -f .env || (umask 077 && cp .env.example .env)
chmod 600 .env
openssl rand -hex 32
```

В корневом `.env` заполните `POSTGRES_PASSWORD` сгенерированным hex-паролем, `BOT_TOKEN` токеном от @BotFather и `ADMIN_TELEGRAM_ID` числовым Telegram user ID. Для существующего тома используйте действующий пароль PostgreSQL. Изменение переменной в `.env` само по себе пароль в базе не меняет. Храните файл и доступ к Docker только у операторов VPS. Для проверки конфигурации используйте `config --quiet`: обычный вывод `config` и `docker inspect` может содержать секреты.

Остановите другие процессы с этим токеном, включая локальный бот. Затем выполните:

```sh
docker compose -p zaynest-prod -f compose.prod.yaml config --quiet
docker compose -p zaynest-prod -f compose.prod.yaml up -d --build
docker compose -p zaynest-prod -f compose.prod.yaml ps -a
docker compose -p zaynest-prod -f compose.prod.yaml logs --tail=50 migrate bot
```

Ожидаемый результат — `db` в состоянии `healthy`, `migrate` завершился с кодом 0, `bot` работает и вывел `bot.started`. Откройте бота как администратор, отправьте `/start`, затем проверьте одну тестовую заявку и `/orders`.

PostgreSQL доступен внутри сети Compose. Данные находятся в томе `zaynest-prod_postgres_data` и сохраняются при перезапуске контейнера. Используйте одинаковое имя проекта `zaynest-prod` при каждом запуске и обновлении. Для обычной остановки используйте `docker compose -p zaynest-prod -f compose.prod.yaml stop`. Удаление тома, в том числе через `down -v`, удаляет данные. PostgreSQL и бот перезапускаются политикой `unless-stopped`; сервис миграции выполняется до запуска бота и не перезапускается автоматически.

Один токен обслуживает один процесс long polling. Имя контейнера `zaynest-prod-bot` защищает от масштабирования и второго запуска этого Compose-бота на том же Docker Engine. Если в журнале есть `telegram.polling_conflict`, проверьте, не работает ли бот с тем же токеном на другом VPS, локально или под другим именем. Остановите лишний процесс перед повторным запуском. При `telegram.token_rejected` проверьте токен, а при `database.startup_failed` — здоровье PostgreSQL и пароль.

## Резервное копирование

Сделайте копию перед каждым обновлением и регулярно при эксплуатации. Следующие команды запускаются из корня репозитория. Дамп записывается в каталог с ограниченным доступом, проверяется и только после этого получает итоговое имя.

```sh
(
  set -eu
  umask 077
  backup_dir="$HOME/zaynest-backups"
  mkdir -p "$backup_dir"
  chmod 700 "$backup_dir"
  archive="$(mktemp "$backup_dir/zaynest-$(date -u +%Y%m%dT%H%M%SZ)-XXXXXX")"

  docker compose -p zaynest-prod -f compose.prod.yaml exec -T db \
    pg_dump -U zaynest -d zaynest -Fc > "$archive"
  docker compose -p zaynest-prod -f compose.prod.yaml exec -T db \
    pg_restore --list < "$archive" > /dev/null
  mv "$archive" "$archive.dump"
  printf '%s\n' "$archive.dump"
)
```

Храните зашифрованную копию вне VPS. Дамп содержит имена, телефоны и черновики. Проверка списка архива не заменяет пробное восстановление. Для такого прогона используйте отдельную PostgreSQL 17 с пустой базой и клиент `pg_restore`. Перед командой задайте `PGHOST`, `PGPORT` и `PGUSER` отдельного тестового экземпляра, настройте доступ через файл `PGPASSFILE` с правами `600` и укажите путь к архиву в `BACKUP_FILE`. Создайте на этом экземпляре пустую базу `zaynest_restore_check`.

```sh
pg_restore --exit-on-error --single-transaction --no-owner --no-privileges \
  --dbname=zaynest_restore_check "$BACKUP_FILE"
```

Проверьте наличие заказов и черновиков в восстановленной базе. Для аварийного восстановления сначала остановите бот, восстановите архив в отдельную пустую базу и проверьте её перед переключением бота.

## Обновление на VPS

Перенесите новую версию проекта, сохранив `.env` и имя Compose-проекта. Проверьте новые миграции, выполните резервное копирование по инструкции выше, затем выполните:

```sh
(
  set -eu
  compose() { docker compose -p zaynest-prod -f compose.prod.yaml "$@"; }
  compose config --quiet
  compose build migrate bot
  compose stop bot
  compose run --rm --no-deps migrate
  compose up -d --no-deps bot
  compose ps -a
  compose logs --tail=50 bot
)
```

Если миграция завершилась с ошибкой, бот останется остановлен. Изучите вывод миграции и состояние Prisma перед повторным запуском. Используйте `prisma migrate deploy` для записанных в репозитории миграций. Первоначальная миграция и последующее добавление статусов и черновиков сохраняют заказы. Миграция статусов выполняется в транзакции и откатывается при неизвестном статусе. Команды сброса базы для обновления не нужны.

## Чек-лист Telegram

- Откройте бота двумя аккаунтами. На аккаунте администратора выполните `/start`. На втором аккаунте проверьте отказ по `/orders`. В группе проверьте, что бот не выдаёт список.
- Создайте заявку с тестовыми данными. Проверьте стоимость обоих тарифов. Введите дробь, ноль и площадь больше 1000 м², имя с цифрой, короткий телефон, чужой контакт. Проверьте приём номера вручную и отправкой своего контакта.
- После телефона проверьте 12 ближайших дат по МСК в трёх колонках. У каждой даты должен быть день недели и число с месяцем. Нажмите «Позже» несколько раз и вернитесь через «Раньше».
- Выберите будущий день и проверьте кнопки с 09:00 до 19:00 с шагом 30 минут и пояснение о демонстрационных часах. Для сегодняшнего дня прошедшие часы недоступны. Нажмите «Назад» и убедитесь, что открывается та же страница дат.
- Выберите время, проверьте московскую дату в карточке и перезапустите бота. Нажмите подтверждение дважды. Клиент должен получить тот же номер заказа, администратор — одно уведомление.
- На календаре отправьте обычное текстовое сообщение, чтобы снова открыть текущий экран. Выберите день на одном из двух экранов, затем нажмите кнопку на другом. Проверьте реакцию на устаревшую кнопку. Нажмите «Отмена» и убедитесь, что старые кнопки не восстанавливают черновик.
- Откройте карточку из уведомления и через `/orders`. Проверьте цепочку `NEW → ACCEPTED → COMPLETED` и отмену отдельного заказа. Нажмите старую кнопку перехода и проверьте актуальный статус через список. При наличии более десяти заказов проверьте переход к старым.
- Начните новую заявку, отмените её кнопкой и попробуйте подтвердить старой кнопкой. Повторите с командой `/cancel`.
- На тестовом боте заблокируйте его с аккаунта администратора, создайте заявку со второго аккаунта и убедитесь, что клиент получил номер. Разблокируйте бота, откройте `/orders` и найдите заявку.
